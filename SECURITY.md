# Security Policy

## Why Private Reporting

Security issues are reported privately first, not because anything is
being hidden from users — but because a public report with no fix
available yet is effectively a how-to guide for attackers targeting
anyone still running the vulnerable version. Reporting privately gives
time to ship a fix before the details go public, which protects users
rather than keeping them in the dark.

## Reporting a Vulnerability

Please do not open a public issue for security vulnerabilities.

Instead, use GitHub's private vulnerability reporting feature:

1. Go to the **Security** tab of this repository
2. Click **Report a vulnerability**
3. Fill out the form with as much detail as possible

Please include:
- A description of the vulnerability
- Steps to reproduce
- Potential impact
- Any suggested fix, if available

This submits the report privately — visible only to the maintainers,
not publicly listed anywhere.

## What to Expect

- An acknowledgment will be sent as soon as possible
- The maintainers will investigate and work on a fix
- Discussion with the reporter happens privately through the same
  GitHub reporting thread
- Once a fix is released, the issue will be published as a GitHub
  Security Advisory — full details disclosed alongside the fix, not
  withheld indefinitely
- Reporters will be credited in the advisory, unless anonymity is
  preferred

## Scope

This policy applies to the code in this repository. Third-party
dependencies should be reported to their respective maintainers.

## Disclosure Timeline

Reporters are asked to allow reasonable time for the issue to be
addressed before independently disclosing it publicly. Once resolved,
full disclosure happens through a published Security Advisory —
nothing stays permanently private.
